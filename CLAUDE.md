# Kartka — сімейний медичний щоденник

> Project brief та інструкції для роботи над продуктом. Цей файл — джерело
> правди про продукт, його межі й технічні рішення. Тримати в актуальному стані.

## 1. Що це

**Kartka** — приватний сімейний медичний щоденник для українських сімей.
Одне місце для всієї медичної інформації родини. **AI не використовується.**

**Серце продукту — АРХІВ:** повна медична картина родини, яку дістаєш і
показуєш (лікарю / у потрібний момент). Щоденний трекінг ліків + нагадування —
**найважливіша функція всередині архіву**, що тримає його актуальним, **але не
другий центр ваги**: трекінг обслуговує архів, не змагається з ним. Перевірка:
людина без регулярних ліків усе одно має повноцінну цінну Kartka (картка +
історія + екстрений екран + PDF).

**Мета:** прибрати хаос із паперами й ризик «загубив виписку / забув ліки /
не пам'ятаю, що призначали», і дати змогу за секунди поділитися повним
анамнезом з лікарем.

**Аудиторія:** дорослі, що ведуть здоров'я **своє та/або родини**. Базовий
сценарій — вести **власну** картку (повноцінний, не урізаний); типове розширення
— догляд за дітьми та/або літніми батьками. Головне для них: менше паперового
хаосу, приватність, готовність показати все лікарю за секунди.

**Хто і навіщо** (стисло; деталі — [`research/personas.md`](research/personas.md) і [`research/jtbd.md`](research/jtbd.md)):
- **Primary-персона — Координатор (двошаровий):** дорослий-власник; **база** —
  веде власну картку, **розширення** — 2–4 профілі рідних (діти / літні батьки).
  Усі сценарії пишемо з його позиції.
- **Main job:** коли хтось у родині має справу з лікарем / ліками / аналізами —
  мати всю медичну картину родини під рукою й діставати потрібне за секунди.
- **Ядро MVP — 3 диференціювальні jobs:** **R1** швидко зафіксувати вхідне (→ фіча
  2) · **R2** показати повну картину за секунди, офлайн (→ фіча 6) · **R5**
  готовність до критичного без мене (→ фіча 7). Фічі 3/4/5 — table-stakes.

**Навігація та головні шляхи** (стисло; повна IA — [`sitemap.md`](sitemap.md) і [`flows.md`](flows.md)):
- **Глобальна навігація:** Головна (дашборд) · Записи (архів за типами) · ➕ Додати ·
  Показати (анамнез). Перемикач профілю та 🆘 Екстрене — у шапці (наскрізні, не таби).
- **Глибина до головної дії** *(«тапи **з дефолтами**» — конвенція підрахунку в
  [`sitemap.md`](sitemap.md), розділ «Навігація»)*: додати документ (R1) — **≤3 тапи**
  (➕ → тип → знімок) + до 1 системного кроку вперше (дозвіл камери); показати анамнез
  (R2) — **2 тапи** з дефолтами (+2–3, якщо міняти обсяг / мову); екстрена картка (R5) —
  **1 тап**, офлайн. *Число — чесна міра глибини, не самоціль: «3 кліки» — міф (NN/g).*

**Платформа:** мобільний веб / PWA (mobile-first, встановлюється на домашній
екран без app store), далі адаптив до десктопу.

**Формат проєкту:** особистий портфоліо-проєкт. Фокус на якості UX, UI та чистій
архітектурі. Без публічного запуску, платежів і масштабування зараз — але
архітектуру й приватність робимо по-дорослому.

## 2. Головний продуктовий принцип

Дані вводяться **вручну** — тому введення має бути максимально швидким і
безболісним:

- мінімум полів;
- розумні значення за замовчуванням;
- шаблони;
- повтор останнього запису.

**Якщо введення дратує — продуктом не користуватимуться.** Це критерій №1 при
будь-якому дизайн-рішенні: спершу питати «скільки тапів і полів це коштує
користувачу».

## 3. Ключові фічі (MVP)

1. **Профілі членів сім'ї** + базова картка: алергії, хроніка, група крові.
2. **Документи** — виписки, результати, файли як прикріплені фото/файли з
   кількома ключовими полями (дата, лікар, тип). **Без AI-розбору.** Тип —
   **пресети** (виписка/епікриз, направлення, рецепт, результат аналізу,
   довідка, висновок), не жорсткий перелік.
3. **Трекінг ліків** по кожному члену сім'ї: що приймає, дозування, період,
   історія прийому. Видно, хто що приймає, щоб уникати конфліктів.
4. **Трекінг аналізів** — результати з датою (+ прикріплений файл), історія за
   параметром у часі. Модель — **гібрид**: каталог популярних показників
   (гемоглобін, глюкоза тощо) з одиницями + можливість додати свій параметр.
   Графіки в часі й автодоповнення. **Лише сира крива значень у часі — без
   референсних норм, кольору-зон, «відхилень», оцінок чи обчислених висновків**
   (інакше це SaMD — медвиріб; див. розділ 4).
5. **Нагадування про прийоми до лікарів**, зокрема повторювані (планові чекапи,
   щорічні огляди, стоматолог раз на пів року тощо).
6. **Експорт анамнезу в PDF** — компактний документ для одного члена сім'ї:
   хроніка, алергії, поточні ліки, останні аналізи, історія візитів. Для
   швидкого шерінгу з лікарем. **Уніфікованої обов'язкової форми пацієнтського
   анамнезу немає** — лікарю важливий зміст, не бланк (приймають будь-який
   зрозумілий). Форму 027/о беремо лише як **чек-лист корисних полів** (діагнози
   основний/супутні, ліки, алергії, обстеження/результати, дати/заклад), **не**
   як шаблон для копіювання. Пріоритет — читабельність і повнота під сценарій
   «лікар проглядає за 10 сек»; обсяг/групування — дизайнерське рішення.
7. **Екстрений екран** — усе критичне на одному екрані. Тут же — кнопка
   **«Знайти лікарню / травмпункт поряд»** із переходом у зовнішні мапи
   (Google/Apple Maps): зовнішній handoff, **без передачі даних пацієнта** (лише
   загальний геозапит на кшталт «лікарня/травмпункт»), **без тріажу й оцінки**
   «куди краще». Власний каталог закладів не будуємо.

## 4. Межі продукту (тримати з 1-го дня)

- **Це НЕ медичний продукт.** Жодних діагнозів, порад чи висновків — лише запис
  і організація даних. Ніякої інтерпретації показників, ніяких референсних норм.
  **Чітка межа (за наміром використання):** зберігання / відображення / пошук
  даних = **не** медвиріб; інтерпретація (зони норми, «відхилення», оцінки,
  обчислені висновки) = медвиріб (**SaMD**). Лишаємось виключно на боці зберігання.
  **Уточнення про рекомендації:** Kartka **зберігає й показує** рекомендації та
  призначення, що їх дав **лікар**, але **сама ніколи не генерує** порад/висновків
  — продукт **не радить**, він пам'ятає те, що сказав лікар.
- **Дані особливої категорії** (чужі, родичів): шифрування ще до запису в базу,
  згода членів сім'ї, відповідність GDPR / закону про захист даних.
- **Жодних зовнішніх AI-сервісів** і відправки медданих третім сторонам.
  Уточнення: зовнішні **переходи-handoff** (напр. «лікарня поряд» → мапи)
  дозволені, **якщо не передають даних пацієнта** — лише загальний геозапит.
  Це не суперечить забороні на відправку медданих третім.
- **Екстрена картка — на присутньому розблокованому пристрої Координатора.** Повний
  сценарій «коли мене немає поряд» (доступ до критичного без пристрою Координатора)
  **свідомо поза MVP** — PWA не дає lock-screen (§6); фізичний артефакт носія
  (друкований QR / картка алергій при дитині/літньому) — можливе майбутнє, не тепер.

## 5. Дані та приватність

- **Модель зберігання:** хмара з шифруванням at-rest (ключі на сервері).
  Обрано свідомо замість E2EE: для родинного шерінгу й — головне — для надійного
  відновлення доступу. Для медичного архіву «втрата ключа = втрата даних»
  неприйнятна (дані можуть бути критично потрібні саме тоді, коли доступ
  втрачено).
- **Ізоляція доступу:** через row-level security (RLS) на рівні БД, **НЕ** через
  логіку в застосунку. Кожен користувач/родина бачить лише свої дані.
  **Правило: жоден доступ до даних не покладається на `where` у коді — тільки на
  RLS-політики.**
- **Файли** (виписки, результати) зберігаються з тими самими RLS-правилами
  доступу, що й рядки БД.
- **Готовність до E2EE:** шар даних спроектувати так, щоб у майбутньому можна
  було додати E2EE для найчутливіших полів без переписування. Поля-кандидати на
  E2EE позначити, але саме E2EE поки **НЕ** реалізовувати.
- **Експорт і видалення (GDPR Art 20 / Art 17) — ✅ спроєктовано:** **експорт усього
  будь-коли** (це й анти-lock-in принцип, не лише право) + **два рівні видалення**:
  **профіль** (прибрати одного члена; акаунт лишається) і **акаунт** (стирання всього
  домогосподарства). Гальма пропорційні незворотності: перелік того, що зникне →
  пропозиція експорту спершу → **пароль** → **30 днів на скасування** → лист.
  Видалення **не ховаємо** (рівний пункт поруч з експортом). Профілі померлих
  **не видаляються авто** — архівний стан. Потік і стани — [`flows.md`](flows.md) +
  [`wireframes/_screens.md`](wireframes/_screens.md).
  ⚠ **Потребує юридичного погляду (не дизайнерського):** хто **контролер** даних рідних
  у моделі «один акаунт на домогосподарство» і як технічно збирається **згода членів
  сім'ї** (обіцянка §4). **Зафіксоване обмеження MVP:** стирання може запросити лише
  **власник акаунту** — родич сам не може (multi-user поза скоупом, §6).
- Жодних зовнішніх AI-сервісів і відправки медданих третім сторонам.
- **Повна автономність від ЕСОЗ/Helsi.** Жодної API-інтеграції: інтеграція з
  ЕСОЗ вимагає сертифікації як ПІС (тех + безпекове тестування) — недосяжно для
  пет-проєкту; до того ж чутливі записи в ЕСОЗ закриті навіть від лікарів.
  **Імпорт — лише ручний** (фото/файл), не через API.

## 6. Технічний стек

- **Frontend + серверні хендлери:** Next.js (App Router), деплой на **Vercel**.
- **Backend:** **Supabase** — Postgres (з RLS-ізоляцією по родинах), Auth
  (сімейні акаунти), Storage (файли виписок/аналізів). Усі три з однієї
  інтегрованої точки.
- **Доступ до даних** — через клієнт Supabase (передає контекст користувача в
  RLS-політики). **Prisma поки не додавати**; розглянути пізніше лише за реальної
  потреби в складній типізації (з урахуванням, що Prisma не застосовує RLS
  автоматично).
- **Auth:** email + пароль. Один акаунт на домогосподарство, усередині — кілька
  профілів (діти, батьки). Multi-user/запрошення — поза скоупом MVP, але модель
  даних не має цьому заважати.
- **PWA:** manifest + service worker, встановлення на домашній екран.
- **Екстрений екран:** окрема **офлайн-закешована сторінка** (service worker) із
  входом **без логіну** на сам екран + **home-screen-ярлик**. Від показу на
  lock-screen **відмовляємось** — технічно наразі недосяжно в PWA на iOS (WebKit: немає
  віджетів / lock-screen).
  **✅ РІШЕНО (P0, варіант «а» — обіцянку R5 звужено):** обидва входи в екстрену
  картку (офлайн-ярлик + 🆘 у застосунку) живуть на **пристрої Координатора**. Тому
  **обіцянка R5 = «швидкий доступ до критичного на присутньому розблокованому
  пристрої Координатора»** (не «коли мене немає поряд» для самого Носія).
  **Зафіксоване обмеження:** шлях «носій без пристрою Координатора» Kartka
  **свідомо НЕ закриває** — PWA не дає lock-screen (вище); фізичний артефакт носія
  (друкований QR / картка алергій при дитині/літньому) — **поза скоупом MVP**
  (можливе майбутнє). Деталі потоку — [`flows.md`](flows.md) (R5).
- **Нагадування:** web push; врахувати обмеження iOS (push у PWA працює лише
  після встановлення на домашній екран) і закласти запасний варіант (локальні
  нагадування / email).
- **PDF-анамнез:** генерація на сервері (Next.js route handler) зі збережених
  даних, локально, **без AI**.
- **Мови:** українська (основна) + англійська. Закласти i18n-структуру з 1-го
  дня.

## 8. Робочі правила для розробки

- Кожне дизайн-рішення міряти «вартістю введення» (тапи/поля) — див. розділ 2.
- Доступ до даних — лише через RLS, ніколи через `where` у коді (розділ 5).
- Жодного AI й жодної відправки медданих третім сторонам — без винятків.
- Нічого, що інтерпретує дані як медичну пораду (розділ 4).
- Позначати поля-кандидати на майбутній E2EE, не реалізовуючи його зараз.

## 9. Правило: джерело правди (MD → HTML)

**`.md`-файли — єдине джерело правди.** Уся інформація формується, зберігається
й оновлюється **тільки** в `.md`.

- **HTML** (`index.html`, `research.html` тощо) — **лише відображення** того, що
  вже є в `.md`. Його **не редагуємо як джерело** і **не вносимо** туди нічого,
  чого немає в `.md`.
- **Порядок завжди:** спершу `.md` → потім згенерувати / оновити HTML із нього.
- **HTML ніколи не веде — завжди наздоганяє.** Якщо HTML і `.md` розійшлися,
  правда за `.md`; HTML приводимо до нього, не навпаки.
- **HTML оновлюється як наслідок `.md`:** коли `.md`-джерело оновлено й
  закомічено, HTML-відображення (research.html тощо) перегенеровується з нього
  й заливається **тим самим кроком** — щоб HTML ніколи не відставав від `.md`.
  HTML не оновлюється самостійно. **Виняток:** `index.html` та будь-який HTML із
  незакоміченою / ручною роботою — **не чіпати автоматично**; синхронізувати
  лише за явним дозволом.
- **Розмежування джерел (щоб не було двох правд):** **продукт і межі** (суть,
  аудиторія, фічі, що не робимо, технічні рішення) — **`CLAUDE.md`**; **дизайн /
  візуальний шар** (бренд-тон, персоналія, anti-references, дві поверхні,
  доступність) — [`PRODUCT.md`](./PRODUCT.md). Один факт — в одному файлі.

## 10. Вайрфрейми (стан фази)

**Фаза каркасів — ЗАВЕРШЕНА й аудитована** (Крок 9, [`wireframes/_critique.md`](./wireframes/_critique.md)).
Усі MVP-потоки зверстано низькодеталізовано (сіре / структурне, слот-бокси, семантика,
доменний текст, системні контроли) — **mobile-first + responsive-десктоп в одному файлі**
(container queries, **не** окремі десктоп-файли).

- **Покрито:** R1 (Документи: список / додати / перегляд), R3 (Ліки), R4 (Аналізи-крива +
  Візити), R2 (Анамнез-PDF), R5 (Екстрена + базова картка); наскрізне — hub «Записи», швидке додавання.
- **Стани** — строго з матриці [`wireframes/_screens.md`](./wireframes/_screens.md) (не шаблонні 4);
  кожен тупик має вихід або зафіксоване обмеження.
- **Межа витримана наскрізь** (розділ 4): жодних норм / зон / оцінок (аналізи), статистики / стріків
  (журнал ліків), оцінки повноти (анамнез = факт-позначка), порад (нотатки візиту = сирий запис слів лікаря).
- **Структура теки `wireframes/`:** `<екран>[-<стан>].html` (каркаси) · `_conventions.md` (рулбук §0–§9) ·
  `_screens.md` (матриця станів — джерело) · `_critique.md` (аудит + фікси) · `_wireframe.css` + `_wf-nav.js`
  (спільна база + риштування навігації).
- **Перегляд:** GitHub Pages → таб «Вайрфрейми»; або локально `python3 -m http.server` (через `file://` риштування не працює).

Наступна фаза — **tokens → concept** (візуальний шар; [`PRODUCT.md`](./PRODUCT.md)), або добір IA-боргу.

## 11. Голос (мікрокопі / тон UI)

**Як продукт говорить — джерело правди [`wireframes/voice.md`](./wireframes/voice.md)** (принципи P1–P5 ·
Словник «одне поняття — одне слово» · Заборонене · мікрокопі-за-типами). Інвентар усього UI-тексту +
change-log застосування — [`wireframes/microcopy.md`](./wireframes/microcopy.md). Тут **не дублюємо**:
за §9 факт про голос живе в одному файлі.

Стрижень голосу — **межа «не судить»** (розділ 4, наскрізна): продукт каже **що** і **коли**, ніколи не
оцінює / не нормує / не радить від себе. Розмежування з [`PRODUCT.md`](./PRODUCT.md): там —
**візуальний / бренд-тон** (колір, персоналія, anti-references); у `voice.md` — **копірайт / мікрокопі**
(як пишеться кожен рядок UI).
